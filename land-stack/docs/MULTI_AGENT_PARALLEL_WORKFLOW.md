# Multi-Agent Parallel Workflow

Two tracks run in parallel to compress the hackathon timeline. The contract below keeps them interoperable without blocking each other.

## The Split
- **Agent A (Track A)** owns `backend/*`: FastAPI app, SQLAlchemy/GeoAlchemy2 models, Alembic, routers, workflow_engine, ML modules, auth/RBAC, audit, tests. Plus `seed-data/*` loader scripts (seed-data files themselves are a shared contract — see below).
- **Agent B (Track B)** owns `frontend/*` + `infra/*`: React app, all 16 screens, MapLibre/GIS, Nginx, docker-compose, GitHub Actions CI.

Neither agent edits the other's owned tree directly. Cross-track changes go through the shared contract files + SYNC_LOG.

## The Contract Between Them (frozen interface)
These files are the shared contract. Once frozen at Hr 0, they change only via Orchestrator approval + a SYNC_LOG entry, and the change must propagate to both tracks:
1. `backend/openapi.yaml` — the API surface Track B codegens its client types from. Generated by FastAPI; Track B reads it read-only.
2. `docs/DATA_SCHEMA.md` — the canonical field names/types both tracks must match exactly.
3. `seed-data/*` — the seed records both tracks demo against (parcels, ror, registration, encumbrance, zoning, building_permission, tax, users, state_adapter_config).
4. `docs/RBAC_MATRIX.md` — the role/permission/masking rules both tracks enforce identically.

Rule: a change to any contract file that affects the other track is blocking — log it in SYNC_LOG before merging, and notify the other track.

## Git Worktree Setup
From the repo root, initialize the main repo and two worktrees so both tracks commit independently but share the frozen contract files:
```bash
# initialize trunk
git init -b main
git add . && git commit -m "chore: initial land-stack scaffold"

# Track A worktree (backend)
git worktree add ../land-stack-track-a -b track-a

# Track B worktree (frontend)
git worktree add ../land-stack-track-b -b track-b
```
Each agent works in its own worktree directory. Contract files live in the shared docs/ + seed-data/ + backend/openapi.yaml and are identical across worktrees (same branch base).

## Sync Cadence
- Every ~1 hour, each agent updates docs/SYNC_LOG.md with what changed and whether it affects the other track.
- The Orchestrator reviews SYNC_LOG at each cadence and resolves any contract drift.
- If a contract file must change, the Orchestrator updates it on `main`, both tracks rebase, and both confirm the change is absorbed.

## SYNC_LOG Format
| Column | Description |
|---|---|
| Time | Sprint hour (e.g. "Hr 2") |
| Agent | Which agent/track made the change |
| Change | One-line description of what changed |
| Affects other track? | "Yes — <file>" or "No" |

Append-only; never edit historical rows.

Example rows:
| Time | Agent | Change | Affects other track? |
|---|---|---|---|
| Hr 0 | - | Repo + worktrees initialized | - |
| Hr 1 | Track A | Added registration router + openapi export | Yes — openapi.yaml (new endpoints) |
| Hr 1 | Track B | Scaffolded Parcel 360 against openapi.yaml | No |

## Conflict Resolution Rules
1. **Contract drift** (a track diverges from frozen contract): Orchestrator reconciles — the contract wins; the diverging track is updated to match.
2. **openapi.yaml mismatch** (frontend expects an endpoint the backend renamed/removed): backend's exported openapi.yaml is authoritative; frontend regenerates client types.
3. **DATA_SCHEMA.md field rename**: requires Orchestrator sign-off, a SYNC_LOG entry, and a backend model migration + frontend type regen in the same PR.
4. **Seed-data change**: must be reflected in both the loader (Track A) and any seeded UI expectations (Track B).
5. **Both tracks edit the same contract file simultaneously**: last-writer-rebases onto the other's change; Orchestrator mediates if the edits conflict semantically.
6. **Non-contract files**: each track owns its tree; no cross-editing. If a fix is needed in the other tree, file a SYNC_LOG note + request, don't edit directly.

## What Each Agent Should Do If Blocked
- **Blocked on a contract file change needed**: write the proposed change + rationale to docs/SYNC_LOG.md, mark "Affects other track? Yes", and ping the Orchestrator. Do NOT unilaterally edit the contract.
- **Blocked waiting on the other track's output** (e.g. frontend needs an endpoint not yet built): implement against the frozen openapi.yaml contract using the documented response envelope; if the endpoint is stubbed, use the standard envelope shape and a TODO. Do not block.
- **Blocked on a schema ambiguity**: check docs/DATA_SCHEMA.md and docs/RBAC_MATRIX.md first. Still ambiguous → SYNC_LOG note + Orchestrator decision; the Orchestrator is the single source of truth for contract interpretation.
- **Blocked on tooling/build**: DevOps Agent owns infra; non-infra agents file a SYNC_LOG note rather than editing infra configs directly.
- Default behavior when blocked: keep building against the frozen contract, log the blocker, continue with unblocked work. Never silently violate a contract rule.

## Final Integration Pass
Before the demo, the Orchestrator runs a single integration pass:
1. Merge `track-a` and `track-b` into `main`.
2. Confirm frozen contract files are byte-identical in intent across the merged tree.
3. Run `docker-compose up` from a fresh clone — this is the judge experience. Both backend (http://localhost:8000) and frontend (http://localhost:3000) must come up healthy.
4. QA/Docs Agent runs the Workflow B core demo end-to-end (registration → mutation → tax) and verifies the Sync Monitor shows it live.
5. Audit chain integrity verified on the Audit Trail Viewer.
6. Standard Technical Document compiled from docs/*.md + exported openapi.yaml.
7. Any integration failure is fixed on the responsible track and re-integrated; do not patch across tracks during integration.
